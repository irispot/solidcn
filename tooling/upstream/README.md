# Safe upstream update review

The original React files and tests stay unchanged. The Solid port stays in separate
`packages/solid` directories. This avoids text conflicts in original files. It does
not make React-to-Solid behavior updates automatic.

## Two-command candidate workflow

```sh
npm run upstream:check
npm run upstream:candidate -- shadcn-ui HEAD
```

Use `base-ui` for Base UI. Replace `HEAD` with an existing local candidate ref or
commit. The tool resolves the ref to an exact commit. It does not fetch, check out,
merge, rebase, change refs, or update a baseline.

The first command detects record, source, generator, override, dependency, and
native-file drift. Its `passed` field means that the records are current and the
selected generated bytes match. It does not accept pending behavior work.

The second command prints a `reportPath` in a new system temporary directory.
Open that report and review `diffs/`. The directory contains:

- `baseline/`: output generated from the pinned source blobs.
- `candidate/`: output generated from the candidate source blobs.
- `unpatched/`: candidate output before explicit overrides.
- `current/`: native-file comparison snapshots, not generators.
- `diffs/`: pinned-to-candidate and current-to-candidate text differences.
- `report.json`: exact commits and source blobs, changed paths, protected test
  changes, generator errors, manual exceptions, and pending reviews.

No output is applied to a live source file. There is no custom output-directory
option. Each candidate run creates a new temporary directory and uses exclusive
file creation. Keep a report if it must survive normal temporary-file cleanup.

Both source submodules start at pinned commits. Thus a checked `HEAD` trial
compares each pin with itself. Fetch an official upstream ref before you review
a newer candidate. The tool has not been validated against a different real
upstream revision yet.

## Proven replay scope

The replay checks cover 99 files: 49 Shadcn wrappers, nine stylesheets, and 41
Base UI leaf export files. Export-file replay is not component implementation
replay. All component behavior remains unaccepted.

The wrapper generator parses the pinned upstream TSX. It converts top-level
stateless wrappers, with a separate reactive prop scope for each function. Each
function must have one typed object parameter and one JSX return. It converts
supported imports, JSX class attributes, and native prop types. A React namespace
import is removed only after a check that every use is the supported
`React.ComponentProps` type. Runtime React uses and other React types fail.
Nested functions, hooks, setup statements, conditional returns, and unsupported
calls also fail. The generator retains the established import header to avoid
unrelated native diffs. These rules remain in `simple-wrapper.mjs` for the first
seven wrappers.

The separate `stateless-wrapper.mjs` supports 42 more wrappers. It adds literal
CVA definitions, selected React type aliases, native primitive prop types,
reactive object getters, native render functions with merged props, data
attributes, and known local/icon imports. It does not execute upstream code.
Hooks, event callbacks, setup computations, and unknown calls fail. Recipes list
exact `Pick` type annotations that must become optional to keep the current
native API. A changed annotation or occurrence count fails for review.

The Base UI entry generator reads original export declarations. It takes export
names from source and routes them to a declared native group. Each recipe has an
explicit current type policy: grouped, selected, or omitted types. A change in
the original type export surface fails. This preserves current native exports;
it does not claim that all original public types or component contracts match.

The style generator reads the upstream CSS and applies the recorded formatter.
Some current styles have formatting differences from the raw upstream bytes.
They are generated from source plus formatter settings, not copied from a native
snapshot. Separate exact-context overrides supply Separator's native prop type,
correct KbdGroup's type to match its `kbd` element, and retain Card's existing
`dataValue` call for its `data-size` attribute. Two more small overrides retain
Input's native primitive type and Progress's reactive prop order.
An override fails when its expected context is missing or appears more than once.
There is no fuzzy patch application.

```sh
node tooling/upstream/check-replay.mjs
node tooling/upstream/check-generators.mjs
```

This read-only check verifies all records and selected replay equality. It also
verifies that changed upstream class/CSS input changes the generated output,
multiple functions use separate prop scopes, unsupported React uses and wrappers
fail, override mismatches fail, and scratch path escapes fail. It does not read or
change original tests. The second command also runs alone while unrelated native
files are under review. It changes source inputs in memory for all 83 newly
supported files and verifies changed output. It rejects changed type surfaces
for all 41 entry files. Two checked-in synthetic source versions exercise CVA,
defaults, render attributes, and prop getters. These are generator checks, not a
claim that a different real upstream Git revision has passed candidate review.

## Per-module records

`records/<repository>/<native-local-path>.json` is one record per native file.
Small separate records reduce conflicts when different modules change.

Each record has the pinned commit, exact upstream source paths and Git blob IDs,
current native SHA256, mapping scope, per-source review status, and a manual
exception where needed. For generated files it also has the recipe, generator and
support-file hashes, override hashes, exact tool versions, dependency-lock hash,
and output hashes before and after overrides.

The current records cover 136 native files:

- 99 have confirmed source-regeneration equality.
- 37 remain `manual-review-pending` for source replay.
- No record accepts component behavior. Every `acceptedBehavior` field is false.

Base UI grouped engines have per-source reference records. Their mappings are
family-level review relationships, not exact function origins. The engines and
the other Shadcn wrappers remain hand-maintained. Their observed hashes are not
generators and do not reconstruct their patch history. External React engine
implementations are not pinned as source blobs where the record says so.

The separate `icon-data.ts` record includes the declared source hashes for 16
Lucide 0.474.0 icons, registry-reference Git blobs, and package lock/license hashes.
`node tooling/generate-icons.mjs --check` verifies those current native data bytes.
That external-package check is not one of the 99 Git-ref replay recipes. The icon
renderer and icon data remain behavior-review-pending.

The remaining 37 files are explicit gaps:

- Base UI: six grouped engines, the merge-props utility, the root export file,
  and the types, use-render, and media-query entry files.
- Shadcn wrappers: Combobox, Drawer, Field, Input Group, Input OTP, Sidebar,
  Slider, Toast, and Toggle Group. Their hooks, callbacks, derived setup values,
  or manual changes need separate rules and review.
- Shadcn engines: Calendar, Carousel, Chart, Form, Sonner, and the five internal
  Command, Input OTP, Message Scroller, Questionnaire, and Resizable engines.
- Shadcn support: icon data, icon rendering, root exports, style integration,
  extracted theme, use-mobile, and shared utilities.

The generated files do not remove those gaps. In particular, generating an
export that points to a grouped native engine does not generate that engine.

Use this read-only command to propose one updated record after a source review:

```sh
node tooling/upstream/replay.mjs propose-record shadcn-ui/packages/solid/src/separator.tsx
```

It writes JSON to standard output, not to the record file. Review and apply that
record separately. Do not refresh hashes simply to hide a drift error. A proposal
never marks behavior accepted. Behavior acceptance needs named source reviews
and evidence from the relevant unchanged tests, native interactions, and pixels.

## Add a generator or a targeted override

No replay-engine edit is needed to add module support:

1. Add a reviewed module in `generators/` that exports
   `async generate({ inputs, options })` and returns source text. Inputs contain
   exact Git-blob content. The generator must not read native output or write
   files. Never execute code supplied by an upstream source file.
2. Add `recipes/<repository>/<native-local-path>.json`. Name the native module,
   generator, exact upstream input paths, all imported local support files,
   dependency package names, and an ordered override list. Use the existing
   recipes as the schema.
3. Put each justified exact-context override in its own `overrides/*.json` file.
   Record its purpose and exact replacement count. Do not use a whole native
   file as an override or call such a snapshot a generator.
4. Generate a record proposal. Prove equality to the reviewed native output.
   Check changed input and unsupported input cases. Then add the per-file record.
5. Run `check-replay.mjs` and a candidate trial. Review all emitted diffs.

Recipes and generators are trusted local maintenance code. They are not a
sandbox for unknown downloaded scripts. Declare all helper files and dependencies
so their hashes and versions participate in the drift check.

## Review and apply an upstream change

1. Run the test-preservation guard and the record check.
2. Obtain a candidate ref through a separate, deliberate Git operation.
3. Generate a candidate. Review all changed source blobs, tests, runners,
   unmapped paths, manual modules, and failed overrides. An unchanged generated
   wrapper does not prove that its Base UI dependency is unchanged.
4. Apply reviewed native changes separately. Keep behavior and formatting changes
   separate. Do not edit old tests to obtain a pass.
5. Run the unchanged-suite adapter, native browser checks, type/export checks,
   and relevant visual cases. Record failures and coverage gaps.
6. Accept any new upstream pin and test baseline only through a separate explicit
   review. Keep prior commit IDs and reports. Do not overwrite checksum baselines
   from a modified working tree.

There is no one-command behavior rebase for the complete port. This tool makes
candidate generation and review simple for the recorded subset, and makes the
remaining manual work visible.

## Existing read-only tools

```sh
node tooling/upstream/impact.mjs status
node tooling/upstream/impact.mjs compare base-ui HEAD
node tooling/upstream/impact.mjs map base-ui packages/react/src/button/Button.tsx
node tooling/upstream/provenance.mjs
```

The impact map includes direct modules and import dependents. It is conservative,
not proof of compatibility. The provenance command reports current source
relationships and preserved migration-script history. Its historical replay
fields do not certify the new safe recipes; use `replay.mjs check` for that proof.

The scripts in `shadcn-ui/packages/solid/scripts` are migration history. They can
overwrite manual fixes and are not a safe repeatable build. Do not run them over
the live port. Base UI's entry generator makes exports only; it does not translate
component implementations.
